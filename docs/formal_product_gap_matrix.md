# 正式版能力差距与实施边界

本表把现有真实 Web、平台仓储和求解能力映射到《正式版项目状态机》与《Rule V2 正式数据模型》。正式版界面只展示已经有后端事实源或本轮明确补齐的数据，不用静态演示冒充完成能力。

| 领域 | 现有可复用能力 | 正式版缺口 | 本轮处理 |
| --- | --- | --- | --- |
| 项目与版本 | `workspace_snapshots / workspace_versions`、乐观并发 revision、审计事件 | 没有一等项目状态聚合、派生阶段、下一步和允许操作 | 新增 Project State 服务与 API，所有页面统一消费 |
| 学期日历 | 统一星期常量、白天/晚自习和周末约束 | 没有学期起止、A/B 周、固定公休、临时停课和日期覆盖模型 | 新增 Term Calendar V1，并兼容现有星期配置 |
| 教师定位 | 教师任教学科导入、Web 保存、已知教师校验 | 没有清晰的任务完成状态和版本化校验结果 | 纳入准备度状态；保留 Excel 导入并增加结果摘要 |
| 年级学科课时 | 课时表、白天课位和 readiness 检查 | 缺少面向教务的年级完成度与异常修复入口 | 生成按年级汇总、缺失/重复/零课时阻断项 |
| 场地与固定事项 | 场地、走班、教研、班级活动等教务表及风险检测 | 信息分散在大而全的教务表；与排课准备流程脱节 | 正式流程只提取资源、合班/同步、固定活动；其余留在更多工具 |
| 规则目录 | 约 93 条成熟规则、硬/软、权重、目标与部分例外编辑 | 业务层级、强度、状态混杂；没有有效期、不可变版本和规则集快照 | 用只读适配器投影为 Rule V2，再逐步切换编辑入口 |
| 自然语言规则 | 国内模型路由、配额、来源、草案、人工确认、两类安全白名单映射 | 只能表达两类教师禁排，不能表达完整对象、时间、例外和复杂关系 | AI 输出 Rule V2；明确 supported/partial/unsupported；不允许静默降级 |
| 求解任务 | 持久化队列、Worker、心跳、取消、任务绑定 workspace revision | UI 没有真实 `validating/compiling/finding/optimizing/packaging` 阶段 | 在状态文件和 API 中规范化 phase；前端删除伪百分比 |
| 诊断与优化 | 冲突检测、诊断试跑、历史比较、质量计划、规则解释 | 分散在“问题处理”和结果页，缺少以候选为中心的闭环 | 合并为方案审查页：诊断、自然语言调整、再求解、版本比较 |
| 人工微调 | 调课预览/应用、影响教师和班级、留痕 | 入口隐藏且会让用户误解为单独工具 | 进入候选审查；每次应用形成新候选版本 |
| 候选与发布 | 推荐候选、发布评估、交付包、版本时间线 | 没有统一 candidate 实体与 freshness 守卫 | 新增候选摘要和 stale 规则；审批/发布只接受 fresh 候选 |
| 身份与 SaaS | 组织、用户、会话、CSRF、RBAC、审计、模型用量 | 登录页只有技术型表单，没有产品欢迎与价值说明 | 增加公共欢迎页；工作台仍走现有服务端认证 |
| 前端信息架构 | 真实 API 已覆盖主要能力；桌面/390px 基础可用 | 单页脚本过大、导航按功能堆叠、规则和结果缺少流程闭环 | 按状态机重组导航和页面；保留底层 API，先进功能渐进披露 |

## 首轮正式版必须真实完成

1. 公共欢迎/登录页、项目首页和 5 阶段主导航；欢迎页明确表达“AI 个性化规则建模 + 工业级求解”。
2. Project State V1：准备度、规则集、求解、候选、下一步和操作守卫。
3. Term Calendar V1：学期日期、单双周、周末排课、固定公休、节次。
4. Rule V2 领域模型、校验器、现有规则适配、规则总览和独立编辑页。
5. AI Rule V2 草案：澄清、结构预览、影响预览、人工确认和不支持状态。
6. 真实求解阶段、任务状态和版本绑定。
7. 候选审查闭环：诊断、规则调整、再优化、比较、微调、审批、发布。
8. 数据/规则变化导致候选过期的服务端守卫。

## 明确不伪造的能力

- 不宣称任意自然语言都能自动变成可求解规则；不支持的语义保留为需求草案。
- 不用倒计时或动画伪装求解进度。
- 不用前端隐藏按钮代替状态机、权限或发布守卫。
- 不把 `edu-ops-scheduler-console` 静态演示当作正式交互产品。
- 不在浏览器下发核心求解器、私有规则实现或模型供应商密钥。

## 实施顺序

1. 以三份合同锁定状态、规则和范围。
2. ImageGen 生成三个独立视觉方向，按业务完整性和可实现性评审。
3. 选定合格方向后，用 Open Design headless 工作流补充欢迎页/设计系统产物；ImageGen 仍为视觉真值。
4. 先实现领域合同与 API，再按视觉稿 1:1 重构真实工作台。
5. 同视口对照设计稿做 Design QA；完成状态迁移、规则、求解、发布和回归门禁。
